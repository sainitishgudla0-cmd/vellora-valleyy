# ADR 0016 — Frontend integration of the backend milestones, and the browser test suite

- **Status:** accepted (M8, 2026-11-12)
- **Context:** M2-M7 added accounts, wholesale, payment states, invoices, tracking and shipping rules as APIs only. The customer UI was "finished and approved" and had to stay visually unchanged; the roadmap makes M8 the milestone that wires the new capabilities in with minimal changes, and moves the browser tests onto a proper runner. New pages normally need design approval; M8 was approved as a milestone, so the new pages reuse the existing visual language only (same containers, headings, `btn`/`input`/`label` classes, sage cards, admin-style tabs) and no new design tokens, and they are flagged below for design review.
- **Decisions**
  - **Existing pages are guarded by a pixel diff, captured BEFORE the change.** `tests/e2e/visual.spec.ts` screenshots 11 existing pages at desktop and mobile (reduced motion, lazy images forced to load, fonts ready) against baselines taken on the pre-M8 code; more than 0.1% of pixels different fails. Result after M8: all 22 identical. Baselines are 48 MB of photographic PNGs, so they are **not committed** (gitignored, per platform); the test skips where no baseline exists (e.g. Linux CI) and the procedure is in the frontend rule and `docs/TESTING.md`. A follow-up could generate Linux baselines from the base branch inside CI.
  - **Customer-facing changes are limited to:** (T1) `CheckoutForm`: a failed order request now explains itself (server message when there is one; a proxy error page or a 5xx says nothing was charged; a dropped connection says the store could not be reached), the delivery fee and serviceability for the entered pincode are shown live from `GET /api/shipping/quote` (an unserviceable pincode is flagged next to the field and the button is disabled; with no shipping rules the wording stays "To be confirmed", exactly as before), and each distinct order request carries an `Idempotency-Key` so a double click or a retry cannot create two orders (a changed form gets a new key). (T4) The order page shows the shipment (courier, tracking number, status, link) and a tax-invoice download once they exist; a new `GET /api/orders/[number]/invoice?t=` serves the PDF to the holder of the order's access token (same convention as the page; no-store, no referrer). (T2/T3) New pages `/account` (sign-in by emailed code, Orders with claim of earlier guest orders, Addresses and details, Business, Privacy) and `/account/orders/[number]` (items, delivery, tracking, history, invoice). The Business tab is the wholesale portal: apply with a GSTIN, status, your own prices, quote requests, accept (with delivery details) or decline. All data comes from the same APIs and services as before; the pages are server-rendered, `noindex`.
  - **Header and footer are untouched**, so no existing page changed. `/account` is reachable by URL only; where to link it (header, footer, order confirmation) is a design decision for the business. Customer sign-in is off in production until a real email sender exists (M5/M7), so the sign-in page honestly says "not available yet" there.
  - **Browser tests run on `@playwright/test`** (1.55.1, exact; the previous `playwright-core` pin and `scripts/e2e-ui.mjs` were replaced; 1.55 satisfies Next 16's optional peer range `^1.51.1`, which 1.48 did not). `playwright.config.ts` drives a running server and a global setup refuses to start unless that server proves its database is disposable. Specs: `guest-journey` (the old script's flow plus checkout messages, delivery quote, tracking, invoice), `account`, `wholesale`, `admin` (owner/team/viewer/password change, shared-password sign-in), `responsive` (overflow at three sizes, menus, reduced motion), `visual`. They run inside `npm run verify:full` and in CI (`VERIFY_UI=1`, system Chrome); traces are uploaded when CI fails.
  - **How tests reach what a browser cannot see.** A test-only route `GET /api/internal/test-environment/otp?email=` returns the newest mock sign-in code, and exists only on a server that is `APP_ENV` development/test AND `CUSTOMER_OTP_MODE=mock` AND declares a disposable database (404 everywhere else, with tests for production, preview, no-mock and non-disposable). `verify:full` starts the server with the mock sender and a fake seller GSTIN only when `VERIFY_UI=1`. Admin steps use an owner account created by the guarded bootstrap script; its session cookie is cached on disk because the admin login is rate limited. `Secure` cookies are not sent by Playwright's request jar over plain http, so authenticated calls use the page's own `fetch`.
  - **Contract tests for every route (M8-T6).** `tests/unit/api-contract-coverage.test.ts` fails when a route file is missing from `API-CONTRACTS.md`, when a documented `METHOD /api/path` has no route or method, or when a route is not exercised by an integration test (its handler imported) or the smoke test. 69+ routes covered; the behavioural contracts (status codes, shapes, authz) are the integration suites that import those handlers.
- **For design review / not done**
  - The new pages follow the site's style but have not been through a design review: layout, copy and spacing of `/account` and its Business tab, and the tracking/invoice block on the order page.
  - No link to `/account` anywhere; no account page for viewing quotes' PDF; wholesale direct ordering (`POST /api/business/orders`) has no UI (quotes only); sign-in cannot be browser-tested against a real sender (M7).
  - Visual baselines exist only on the machine that captured them (macOS); Linux CI skips the visual spec.
