# ADR 0020 — Failed online payments expire; late captures are kept (M11 P1-T3)

- **Status:** accepted (M11, 2026-11-20). Extends ADR 0011 (expiry) and ADR 0018 (webhooks, orphan captures).
- **Context (finding F06):** after a failed payment (`payment.failed` webhook or `/verify` seeing `failed`), the order stays `awaiting_payment` / `failed` and its attempt `failed`, so the customer can retry on the same gateway order. `expireUnpaidOrders` only selected `unpaid` attempts on `unpaid` orders, so a failed order that was then abandoned held its stock reservation **forever**. Reproduced on the pre-fix code by `tests/integration/payment-failed-expiry.test.ts` (11 of 14 new tests failed; the core one with "expected 0 to be greater than or equal to 1" expired orders).
- **Decision:**
  1. **Selection:** expiry now takes `unpaid` **and** `failed` attempts on `awaiting_payment` orders whose payment is `unpaid` or `failed`, past `PAYMENT_WINDOW_MINUTES` (default 60, min 15) from order creation. It never selects an orphan-capture row (`providerPaymentId` set, or an orphan `reconcileReason`): that is captured money waiting for a refund.
  2. **Retry grace:** a failed order whose latest failure event is newer than `RETRY_GRACE_MINUTES` (15) is left alone, even past the window, so a customer who just saw "payment failed" can try again. Inside the window nothing is expired at all.
  3. **Gateway first, unchanged rules:** before cancelling, the gateway order's payments are listed: `captured` → marked paid through `applyGatewayPayment`; `authorized` → left (money held); unreadable gateway → error, retried next run, never cancelled. Only `created`/`failed` (nothing paying) is cancelled.
  4. **Cancellation** is one transaction: claim the attempt in the state that was read (`updateMany where status = read status, providerPaymentId null`, row lock), then `transitionOrder awaiting_payment -> cancelled` (with `unpaid -> failed` for an unpaid order; a failed order keeps `failed`, since `failed -> failed` is not a transition), which releases the stock hold through the ledger and appends the `OrderEvent` (actor `system/expiry`).
  5. **Late captures are never dropped:** if a capture loses the race to expiry (its claim succeeds on the still-`failed` row but its order transition finds `cancelled`, so it rolls back), `applyGatewayPayment` now records it as an **orphan capture** (`captured_on_cancelled_order`; `duplicate_capture` if another payment paid the order). `recordOrphanCapture` moved from `webhook.ts` to `razorpay-verify.ts` for that. The webhook already did this for captures arriving after cancellation.
  6. **Late-capture check:** `reconcileGateway` gains `checkExpiredForLateCaptures`: for 24 h after an expiry, at most once per 10 minutes, it lists the gateway order's payments and records any unknown capture as an orphan (`lateCaptures` count in the reconcile response). This covers a slow UPI/netbanking approval when both the webhook and the browser are lost. It never re-opens the order or re-reserves stock; an owner refunds the orphan (`refunds.ts`).
- **Rejected:** re-opening a cancelled order on a late capture (its stock may already be sold; the customer was told it was cancelled); a schema change for a "retrying" state (the existing `failed` + event history is enough); measuring the window from the last failure only (lets one order hold stock indefinitely through repeated failures).
- **Consequences / limits:** grace is measured from the **first** failure event: a second failure on the same order is acknowledged by the webhook as `failed_ignored` and writes no event. Expiry and reconciliation only run when called: the `vercel.json` crons from M11 P3-T5 (expire every 15 minutes, reconcile four times an hour) need `CRON_SECRET` set in the deployment, so a stuck order can wait up to one cron interval past its window or grace. Verified only against `tests/support/fake-razorpay.ts` (F20; real test-mode run is P6-T2). No migration.
- **Evidence:** `tests/integration/payment-failed-expiry.test.ts` (14 tests: reproduction with event trail, ledger and idempotent re-run; retry inside the window; retry grace; captured retry found by expiry; authorized retry; unreadable gateway; orphan row untouched; capture winning while the sweep waits; capture after expiry → orphan; 8× racing expiry vs verify path; 8× racing expiry vs signed webhook; two concurrent sweeps; late-capture check once and its 24 h limit), plus the existing `order-expiry`, `razorpay-verify`, `razorpay-webhook`, `reconcile`, `payment-lifecycle`, `refunds`, `inventory` suites.
