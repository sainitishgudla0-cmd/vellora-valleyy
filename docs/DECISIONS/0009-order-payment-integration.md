# ADR 0009 — Order/payment integration, gateway ambiguity and reconciliation

- **Status:** accepted (M2-T5, 2026-11-12)
- **Context:** Checkout and Razorpay verification wrote order status directly and trusted the browser's signature alone; a gateway timeout after creating a local order cancelled the order blindly.
- **Decisions**
  - **Creation:** `createOrder` inserts the order, items and its `Payment` attempt in one transaction. Provider and `paymentMode` come only from `safePaymentConfig()`: COD -> `request_only` attempt (order stays `pending_confirmation`, unpaid); mock -> mock attempt with its deterministic simulated reference (no network); Razorpay -> pending attempt with no gateway reference yet.
  - **Gateway call is outside any transaction.** Outcomes (`checkout.ts`): *ready* (reference validated and persisted on attempt and order in one transaction); *definite* failure (gateway 4xx or an answer with the wrong amount/currency/shape): order cancelled and attempt failed through `transitionOrder`; *ambiguous* (timeout, 5xx, 429, lost response, failure persisting the reference): order kept `awaiting_payment`, attempt flagged `needsReconciliation`, 502 with the order number. The client never receives a gateway reference unless it was persisted, so an ambiguous order cannot be paid.
  - **Verification:** server records first (token, gateway reference, `paymentMode` equal to the server's and non-NULL, matching attempt, amount = total, INR), then the HMAC, then a server-side `GET /payments/{id}` that must be `captured` for exactly this gateway order, amount and INR. Authorized/pending -> 202 and flagged; gateway down -> 503 and flagged; mismatch -> 409 and flagged; failed -> attempt/payment `failed` (only from `unpaid`). The paid transition is one transaction: conditional attempt claim + `transitionOrder(awaiting_payment -> paid, payment -> paid, actor gateway/razorpay)`; `Payment.providerPaymentId` uniqueness prevents one payment paying two orders; identical concurrent requests yield one transition.
  - **State machine invariants** added to `validateTransition`: an order only becomes `paid` together with its payment; a payment cannot become paid on a cancelled order.
  - **Legacy orders (`paymentMode` NULL):** never classified or paid automatically. Valid signatures do give cryptographic evidence of the key in use, but a "never guess" policy is simpler to defend; such orders get `409` and are reconciled by an operator. Cost: orders in flight at deploy time need manual handling (runbook).
  - **Reconciliation** (`reconcile.ts`, `npm run payments:reconcile`): completes captured payments with the same code path as `/verify`, attaches a gateway order found by receipt, cancels never-created orders only after a TTL and a successful empty lookup, never acts on an unreadable gateway, and ignores attempts from other modes.
  - **Environment:** `MOCK_PAYMENT_CONFIRM_KEY` in preview/production is a configuration error (build gate; runtime fails closed), warned about when set but mode != mock. Real checkout never reads it. Tests use a fake gateway that throws on any other host.
  - **Mock exercise path:** `npm run payments:mock-checkout` (server-side, guarded, key from its own env) drives real `POST /api/orders` and `mock/confirm`. The storefront is unchanged (mock mode does not enable the online option in the UI).
- **Ratchet:** only the admin PATCH still writes status directly (M2-T6). Two non-status writers attach the Razorpay reference.
- **Remaining risks:** no order idempotency keys or stock reservation (M3); in-memory rate limiting; reconciliation is operator/scheduler-run until M10 webhooks; Razorpay request shapes are verified against deterministic fakes only, not the live API; the Razorpay `receipt` filter on order listing should be confirmed in test mode before relying on it in production.
