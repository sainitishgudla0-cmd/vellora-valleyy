# ADR 0011 — Quantity-aware inventory, expiry and order idempotency

- **Status:** accepted (M3, 2026-11-13)
- **Context:** availability was one manual boolean (`Variant.inStock`); nothing stopped overselling and nothing prevented a double-clicked or retried checkout from creating two orders. The roadmap left four product questions open (real counts vs manual, reservation timeout, backorders, wholesale allocations); defaults below are conservative and reversible.
- **Decisions**
  - **Opt-in tracking, per variant.** `Variant.trackInventory` (default false) switches a variant from the manual `inStock` flag to real counts (`stockQuantity`, `reserved`). Deploying the migration changes no behaviour: every existing variant stays manual until staff enable tracking with an opening count. Tracking can be switched off again (stock is zeroed through the ledger, refused while open orders hold units).
  - **Availability = `stockQuantity - reserved`.** `inStock` stays in every API output, derived for tracked variants (`effectiveInStock`); the stored column is kept in step by the ledger writer so code that still reads it (the admin dashboard) stays right. Counts are never exposed publicly.
  - **Ledger.** `InventoryMovement(reason, stockDelta, reservedDelta, stockAfter, reservedAfter, note, actor, orderId?)`, append-only. `reserve` (+reserved at order creation), `release` (−reserved on cancel/expiry), `fulfil` (stock and reserved both drop on dispatch), `adjustment` (staff, reason required). SUM(deltas) equals the counters (`findLedgerDrift`, asserted at the end of every integration file). `src/lib/inventory/ledger.ts` is the only writer of the counters (ratchet test).
  - **No oversell.** One guarded `UPDATE ... WHERE stock - reserved >= qty RETURNING` per line inside the order-creating transaction; row locks serialise parallel orders and the WHERE re-checks after the lock. Lines are processed in id order (no deadlocks). DB CHECKs are the backstop: stock >= 0, reserved >= 0, reserved <= stock, untracked variants hold no counts.
  - **One transaction for `createOrder`:** read variants, idempotency claim, order + lines + payment attempt, stock holds. A refused line (409 naming product and variant, and how many are left) rolls everything back. Order-number collisions retry the whole transaction with a fresh number (max 3, then a retryable 503).
  - **Stock follows status inside the state machine** (`applyOrderInventoryEffects`, same transaction as the status update): cancel before dispatch releases, dispatch consumes. What an order holds is read from the ledger, so legacy orders and untracked variants have nothing to release and a repeat is a no-op. Cancelling after dispatch does not restock (goods may not come back; staff adjust by hand).
  - **Expiry (`expireUnpaidOrders`, `GET /api/internal/orders/expire`).** Unpaid *online* orders past the window (default 60 min, floor 15, `PAYMENT_WINDOW_MINUTES`) are cancelled by actor `system`/`expiry`, which releases the hold. It first asks the gateway: captured -> the order is marked paid instead; authorized -> left alone; unreadable answer -> skipped; attempts without a gateway reference are left to `payments:reconcile`. Abandoned ("created") or failed gateway attempts do not block expiry. Pay-on-delivery orders are **not** expired: their hold lasts until staff confirm or cancel (see risks). The route is bearer-protected by `CRON_SECRET` (404 unless 24+ characters). **`vercel.json` has no cron entry on purpose:** a sub-daily schedule fails deploys on plans that only allow daily crons, so the operator adds it once the plan is confirmed (runbook).
  - **Idempotency.** Optional `Idempotency-Key` (16-128 chars `[A-Za-z0-9_-]`). Only `sha256("orders:"+key)` is stored with a hash of the canonical request body. The key is claimed inside the order transaction, so a stored key always has an order; the final response (201, or the 502 outcomes) is stored and replayed verbatim with `Idempotent-Replayed: true` for 24 h. Same key + different body -> 422. A request that loses a race, or arrives before the first has finished, gets 409 `Retry-After`. Refused orders (409/4xx) roll the claim back, so the same key can be retried after the cause is fixed.
  - **Admin.** `PATCH /api/admin/variants/[id]` gains `trackInventory` (+ `reason`) and `stockAdjust { delta, reason }` (409 codes `not_tracked`, `negative_stock`, `below_reserved`, `reserved_open`); `inStock` is ignored for tracked variants so the unchanged dashboard (which always sends it) keeps working. `GET /api/admin/variants/low-stock?threshold=` lists tracked variants at or below the threshold (default 5).
- **Consequences / risks**
  - Reservations start at order creation, so unpaid pay-on-delivery orders hold stock indefinitely; a burst of junk COD orders (rate limit is 10 per 10 min per IP, in-memory) can lock units until staff cancel. Consider a COD expiry or confirmation window in a later task.
  - A customer who pays after their online order was expired is charged for a cancelled order (needs a refund; M10). The 60 minute default makes this rare; authorized payments are never expired.
  - The storefront does not send `Idempotency-Key` yet (frontend change needs approval), so double-submit protection is available to API clients but not yet used by the checkout page.
  - The admin dashboard has no stock UI; stock is managed through the API (frontend approval needed).
  - Backorders, pre-orders and wholesale allocations are not modelled.
  - A request that crashed between creating the order and storing its response leaves its key "in progress" for 24 h (clients get 409; the order itself is intact and visible to staff).
  - Order creation events: `OrderEvent` records transitions only (it needs a from-status); creation is evidenced by the order row and the `reserve` ledger rows.
