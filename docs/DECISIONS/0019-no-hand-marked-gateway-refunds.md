# ADR 0019 — Gateway refunds are never recorded by hand (M11 P1-T1)

- **Status:** accepted (M11, 2026-11-14). Supersedes the gateway half of the refund bookkeeping in ADR 0010 / ADR 0018.
- **Context (finding F03):** `PATCH /api/admin/orders/[id]` with `{ paymentStatus: "refunded", reason }` moved any non-mock, non-legacy payment `paid -> refunded`, including captured Razorpay (test and live) payments, without calling the gateway. Three consequences, reproduced by tests on the pre-fix code:
  1. The system could say "refunded" while the customer's money was still captured (no `Refund` row, no gateway refund).
  2. It bypassed the owner-only `refunds:write` permission: `orders:write` is held by **operations** accounts and the **shared-password legacy session**.
  3. Once hand-marked, `createRefund` answered `not_refundable`, so the real refund could no longer be made through the system. A combined `{ status: "cancelled", paymentStatus: "refunded" }` did the same in one request.
- **Decision:** the hand edit `paid -> refunded` is allowed only when **both** the order's recorded `paymentMode` and the payment attempt's `provider` are `request_only` (money that never touched a gateway, e.g. cash on delivery returned in cash). Every other payment is refused with the existing `409 payment_edit_not_allowed` (no new code, no schema change). A gateway payment becomes `refunded` only through `src/lib/payments/refunds.ts` (`settleFullRefund`, actor `gateway`) once processed `Refund` rows cover it: an owner's `POST /api/admin/orders/[id]/refunds`, a `refund.*` webhook, or the reconciliation `--audit-refunds` pass that adopts dashboard refunds.
- **Rejected:** a permission check alone (owner-only bookkeeping) still fabricates a refund with no gateway evidence; an "offline refund of a gateway payment" mode, which needs a defined, separately audited process the business has not specified (tracked under M11 P1-T2/F04, blocked on a business decision).
- **Consequences:** request-only bookkeeping is unchanged (still `orders:write`, reason required; its authorisation is reviewed with manual confirmation in P1-T2). The admin dashboard never offered this edit, so no UI changes. History is untouched: no migration, no rewrite. Per `PROGRESS.md`, production has not received any M2+ migration (no `Payment` table yet) and this code has never been deployed there, so no production row can carry a hand-marked gateway refund (operator to confirm at baselining). A preview/test database could hold one: a `Payment` with `provider = razorpay`, `status = refunded` and processed `Refund` rows summing to less than its amount.
- **Evidence:** `tests/integration/admin-orders.test.ts` ("recording refunds made outside the system": owner, operations and legacy sessions; `razorpay_test` and `razorpay_live`; combined status change; request-only order carrying a gateway attempt) and `tests/integration/refunds.test.ts` ("a status PATCH cannot pre-empt a gateway refund"). Three tests failed on the pre-fix code (200 instead of 409). Removing the attempt-provider guard fails the defence-in-depth test.
