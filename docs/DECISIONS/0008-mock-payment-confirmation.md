# ADR 0008 — Mock payment confirmation and order payment mode

- **Status:** accepted (M2-T4, 2026-11-12)
- **Context:** ADR 0002 reserved `PAYMENT_MODE=mock` for development/test; M2-T3 added the mock provider and `Payment` rows. T4 makes a mock payment confirmable end to end without ever being mistakable for a real one.
- **Decisions**
  - **`Order.paymentMode`** (`PaymentMode?`): the server-resolved mode of the provider that handled the order. Pay-on-delivery is always `request_only` (it never touches a gateway, whatever the global mode); online orders take the configured mode (`mock | razorpay_test | razorpay_live`). Resolved by `resolveOrderPaymentMode` in `createOrder` from `safePaymentConfig()`; the request body has no mode field. **Legacy orders stay NULL** (unclassified): old Razorpay orders are not guessed to be test or live, and nothing treats NULL as mock.
  - **DB CHECKs** (migration `order_payment_mode`): mode and method agree; a mock order cannot hold Razorpay ids; a `Payment`'s provider and mode agree; mock payments only carry `mock_pay_*` ids. `PaymentMethod` is unchanged (a mock online order uses `razorpay` as the *method* the customer chose, with mode `mock`).
  - **`POST /api/payments/mock/confirm`** exists only when the server's own resolved config is `mode=mock` in `development`/`test` (otherwise 404, including when mock is forced in preview/production, where config resolution already fails closed). Authorisation is not the mode: it needs `x-mock-confirm-key` = `MOCK_PAYMENT_CONFIRM_KEY` (24+ chars, constant-time; absent => 404) and the customer's order token. Order of checks: environment/mode (404) -> key configured (404) -> rate limit (429) -> key (401) -> strict body (422) -> service.
  - **Service** (`confirmMockPayment`): order must be `paymentMode=mock` with a matching `provider=mock, mode=mock` attempt, valid mock proof, the deterministic mock payment id, `attempt.amount == order.total`, `currency == INR`, order `awaiting_payment/unpaid`. Anything else is 404 (not mock / unknown / wrong token), 400 (bad proof) or 409 (conflict). The mock proof is a simulation device, not evidence of settlement; the key and token are the authorisation.
  - **Atomicity:** `transitionOrder(input, tx?)` now accepts an optional transaction client (backward compatible). The service claims the `Payment` row (conditional `unpaid -> paid`, amount/currency/provider pinned in the `where`) and calls the same state machine inside one `db.$transaction`; any failure rolls back both and the `OrderEvent`. Concurrent identical requests: one writes, the rest return `alreadyConfirmed`. A cancelled order can never become paid (state machine + conditional update).
  - Actor is `system` / `mock-provider` (not `gateway`), reason "Simulated mock payment: no money moved".
  - **Labelling:** the order page and admin show `MOCK — no money moved` for `paymentMode=mock` and do not say "Payment received"/"Razorpay"; the admin "to action" count excludes mock-paid orders. No fulfilment automation exists.
- **Not in T4 (M2-T5):** checkout creating mock orders and attempts. Until then they come only from test fixtures (`tests/support/mock-orders.ts`); no public endpoint creates paid or mock orders. The browser cannot hold the confirm key, so T5 must trigger confirmation from a dev-only server-side path or script.
- **Consequences:** production cannot reach the route, the key is a dev/test secret only, and mock rows are structurally separable from real revenue.
