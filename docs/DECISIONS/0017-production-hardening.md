# ADR 0017 — Production hardening and release readiness (M9)

- **Status:** accepted (M9, 2026-11-12). Items that need the business or the operator are listed at the end and are **not done**.
- **Context:** M1-M8 built the backend and wired it in. Before the payment gateway goes live (M10) the platform needs response-header hardening, limits that work across serverless instances, logs a monitor can read, a lint gate, a clean dependency audit, proof that a backup restores, and written release and rollback procedures. Several M9 tasks are changes to GitHub, Vercel or the production database; CLAUDE.md forbids doing those from here, so they are delivered as checklists with the exact steps.
- **Decisions**
  - **Security headers (T3)** live in `config/security-headers.mjs` and apply to every route through `next.config.mjs`: a CSP (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri`/`form-action 'self'`, `upgrade-insecure-requests`; Razorpay is the only third-party origin: `checkout.razorpay.com` script/frame, `api.razorpay.com`/`lumberjack.razorpay.com` connect), `Strict-Transport-Security: max-age=63072000`, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/microphone/geolocation off, payment delegated to Razorpay), and `X-Powered-By` removed. **`script-src` keeps `'unsafe-inline'`** because Next streams inline hydration scripts and the root layout has two inline scripts; a nonce-based CSP needs every page rendered dynamically (a performance and frontend change), so it is a follow-up. `unsafe-eval` is added for `next dev` only. HSTS has **no `includeSubDomains` and no `preload`**: both are hard to undo and depend on the custom-domain decision. Proof: `tests/unit/security-headers.test.ts`, header checks in the API smoke test (`/`, `/api/products`, `/account`), and the whole Playwright suite running under the policy (a CSP violation is a console error, which the page-error watcher fails on).
  - **Shared rate limiter (T4).** `rateLimit()` keeps its signature (18 call sites unchanged) and now counts in Postgres: one atomic `INSERT … ON CONFLICT DO UPDATE` on `RateLimitBucket(key, count, resetAt)` per request, so any number of serverless instances share the same window and N parallel requests admit exactly `limit`. Timestamps are written as UTC wall clock (`::timestamptz AT TIME ZONE 'UTC'`) so the DB session time zone cannot skew windows (the M7 outbox lesson; the integration test runs in a non-UTC session). Keys are `bucket:HMAC-SHA256(client IP)`: no raw IP in the database. If the database is unreachable the limiter **falls back to the old per-instance counter** (never fail-open, never blocks customers) and logs one warning a minute. `RATE_LIMIT_STORE=memory` forces the per-instance mode. Expired rows (>1 h) are purged on ~1% of calls. Postgres over Upstash: no new vendor, secret or network hop, and the load is a few writes per public request. If traffic grows, the store is one module (`rate-limit-store.ts`). Deploy order: the table is additive; an app deployed before the migration simply uses the fallback.
  - **Logging and monitoring (T5).** `src/lib/log.ts` writes one JSON object per line (`ts, level, event, service, env, commit` plus fields), redacts fields whose names look sensitive, truncates strings, and is silent under test unless `LOG_LEVEL` is set. All 18 `console.*` calls in `src/` were converted (events such as `payments.verify_conflict`, `orders.create_failed`); a ratchet test fails on any new `console.*`. Error objects and messages are never logged (they can carry customer data): only the class name. `src/instrumentation.ts` `onRequestError` logs every unhandled server error as `request.unhandled_error` with class, digest, route pattern and the path without its query string (order tokens travel in `?t=`). `GET /api/health` is the uptime probe: `200 {ok:true}` or `503 {ok:false}` after a 3 s database check. **Vendor not chosen**: logs go to Vercel's log stream as structured JSON, which any drain (Axiom, Datadog, Better Stack, Sentry via drain) can ingest unchanged; picking one is a business decision (cost, data residency).
  - **Preview database isolation (T2).** Enforceable part: `PRODUCTION_DB_HOSTS` (host names, not secret) is set in every Vercel scope, and `npm run env:check`, the first step of `vercel-build`, fails the build when a **preview** points `DATABASE_URL` or `DATABASE_URL_UNPOOLED` at a listed production host, **or** when a preview has a database but the list is missing (isolation cannot be shown: fail closed), and when **production** points at a host that is not in the list (a swapped variable). Production without the list builds with a warning so the first deploy of M9 cannot break it. CI exercises all three cases. Not verifiable from here: what the Vercel project's Preview scope actually contains (checklist in `docs/RELEASE.md`).
  - **Lint (T6).** ESLint 9 + `eslint-config-next` 16 flat config (`eslint.config.mjs`), `npm run lint` is part of `npm run verify` and CI. Errors fail; the frontend is frozen, so its 12 existing findings (React Compiler `set-state-in-effect`, short-circuit calls in animation setup, one `any` in an admin helper) are **warnings with a ratchet** (`--max-warnings=12`; the number only goes down). Backend and test findings were fixed (unused imports and variables, a dead constant).
  - **Dependency audit (T9).** `postcss` 8.4.49 → 8.5.32 (high advisories) and `tsx` 4.19.2 → 4.23.15 (esbuild advisory), plus an `overrides` entry pinning `minimatch` 11.0.8 under `@typescript-eslint/typescript-estree` (moderate). `npm audit` reports 0 including dev dependencies; CI runs `npm audit --audit-level=high` on every push.
  - **Backup and restore drill (T7).** `npm run db:restore-drill` (disposable source only) does `pg_dump -Fc`, restores into a new scratch database on the same server, compares row counts and an order-independent content checksum for every table, the applied-migration count, constraint and index counts, runs `prisma migrate status` and the drift check against the copy, reports timings, and drops only the scratch database it created. A tampered copy fails it (checked). Evidence and the proposed RPO/RTO are in `docs/RUNBOOK-DATABASE.md`.
  - **Not done from here, by rule (delivered as operator checklists in `docs/RELEASE.md`):** production baselining (T1, hard rule 2), Vercel preview verification (T2), the production restore/PITR drill (T7), branch protection and required CI on `main` and `backend/development` (T8, GitHub settings, hard rule 4).
- **Consequences**
  - A preview deployment without `PRODUCTION_DB_HOSTS` set will fail to build until the operator adds it. That is the point.
  - Rate-limit counters now persist across restarts and deploys; `npm run db:cleanup-tests` clears them on a disposable database so a re-run of the smoke test does not inherit a spent window.
  - CSP will block any new third-party script, font, image host or frame until it is added to `config/security-headers.mjs` (with a test). Adding a payment or analytics vendor is therefore a deliberate, reviewed change.
- **Follow-ups (need a decision):** monitoring/alerting vendor; RPO/RTO targets; nonce-based CSP; HSTS `includeSubDomains`/`preload` once the domain is fixed; self-hosting fonts (removes the build-time Google Fonts fetch that has flaked CI three times: a frontend change); credit notes and the other M7 gaps are unchanged.
