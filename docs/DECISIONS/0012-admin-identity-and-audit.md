# ADR 0012 — Individual admin accounts, server-side sessions, roles and audit

- **Status:** accepted (M4, 2026-11-14)
- **Context:** one shared `ADMIN_PASSWORD` and a stateless signed cookie: no individual accountability (order events could only say "admin"), no way to revoke a session or a person, no roles, no CSRF defence beyond `SameSite=Lax`, no audit trail. The dashboard login form posts `{ password }` only, and customer-facing/admin UI files may not change without approval.
- **Decisions**
  - **Accounts** (`AdminUser`): lower-cased unique email, scrypt hash (`scrypt$N$r$p$salt$hash`, N=2^15, built into Node, no new dependency), role `owner | operations | catalog | viewer`, `active` flag, failed-login counter and lockout. Password policy: 12-200 characters, not trivially repetitive, not containing the email name.
  - **Sessions** (`AdminSession`): the cookie `vv_admin` holds 32 random bytes; the database stores only `HMAC-SHA256(SESSION_SECRET, token)`, so a database read cannot be replayed and the cookie cannot be forged. Absolute life 8 h, idle timeout 2 h, revocable. Logout, deactivation, role change, password change/reset and an owner revoking a session all take effect on the very next request. A new login replaces the session a browser already held (no fixation). Cookies from before M4 are simply invalid: everyone signs in once.
  - **One gate:** `requireAdmin(req, permission)` (`src/lib/auth/admin.ts`) runs the same-origin check for mutations, then the session, then the role's permission: `401` no session, `403` wrong origin or role. Routes ask for permissions (`orders:write`, `catalog:write`, `inventory:write`, `users:manage`, ...), never roles; the matrix is `src/lib/auth/roles.ts` and is written out in full in a unit test. The variants endpoint checks `catalog:write` and `inventory:write` per field, so catalog and operations staff each reach only their fields.
  - **CSRF (T3):** for POST/PATCH/PUT/DELETE a present `Origin` must match the request host (`X-Forwarded-Host` first) or `ADMIN_ALLOWED_ORIGINS`; without `Origin`, `Sec-Fetch-Site` must not be cross/same-site; with neither it is a non-browser client and passes (browsers always send `Origin` on cross-site mutations, and `SameSite=Lax` stays on). Login and logout use the same check.
  - **Lockout:** 5 consecutive wrong passwords lock the account for 15 minutes (counter reset on success; an owner can unlock). Every login failure is the same `401 "Incorrect email or password"` whether the account is unknown, disabled, locked or the password is wrong, and a burned scrypt check evens out timing; the real reason goes to the audit log only. The per-IP rate limit (8 per 15 min) stays.
  - **Audit** (`AuditLog`, append-only, no FK to the user so history survives): logins (success/failure/lock), logout, every admin mutation (success or rejected), every permission/origin denial. Details are ids and field names only: never passwords, tokens, free-text reasons or customer data. A failed audit write is logged without contents and never turns a finished mutation into an error response. Order events and inventory ledger rows now record the account id as the actor (`legacy` for the shared password).
  - **Last owner:** the last active owner cannot be demoted or deactivated (checked under a row lock; two owners demoting each other concurrently cannot both win).
  - **Transition from the shared password (T4):** the unchanged dashboard login form cannot send an email, so `POST /api/admin/login { password }` keeps working while `ADMIN_PASSWORD` is set and `ADMIN_LEGACY_LOGIN` is not `off`. Such sessions are DB sessions flagged `legacy`, treated as owner-level for the existing dashboard actions but **never** able to manage users, and attributed to `legacy` in the audit log. Setting `ADMIN_LEGACY_LOGIN=off` (or removing `ADMIN_PASSWORD`) disables the login and ends live legacy sessions immediately. **Retiring it fully needs a login-form change** (email + password), which is a frontend change awaiting approval (T6).
  - **First owner and recovery:** `npm run admin:bootstrap -- --email … --name …` (guarded by `scripts/db-guard.ts`, production needs the explicit confirmation) creates the first owner only; the password comes from `ADMIN_BOOTSTRAP_PASSWORD` or a hidden prompt and is never printed, logged or an argument. `-- --reset --email …` resets an owner's password, ends their sessions, clears lock and deactivation. That script, run by someone with database access, is the owner-recovery process; there is no email-based reset.
  - **Account API instead of UI:** owners manage accounts, sessions and the audit log through `/api/admin/users`, `/sessions`, `/audit` and staff change their own password via `/account/password`. No admin UI was built (see T6 below).
- **Not done / consequences**
  - **M4-T6 (admin UI for users and sessions) is not built:** it is a customer-visible-adjacent frontend change and the task said to confirm scope. The API is complete, so a UI is a thin layer.
  - **2FA (TOTP) is deferred.** Lockout, scrypt, individual accounts and revocable sessions come first; TOTP fits as a second step in `loginWithPassword` plus a `totpSecret` column.
  - The shared password stays valid until the owner turns it off; until the login form is updated, turning it off locks staff out of the web form (the API login works).
  - Locked accounts give no hint to the person (same 401); the owner unlocks via `PATCH /api/admin/users/[id] { unlock: true }` or the lock expires.
  - Session `lastSeenAt` is refreshed at most once a minute, and an in-memory login rate limit is per server instance (unchanged from before).
  - The audit log is not yet rotated or archived; at admin volumes it is small.
