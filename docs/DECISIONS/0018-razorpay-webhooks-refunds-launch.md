# ADR 0018 — Razorpay webhooks, reconciliation, refunds and the gated launch (M10)

- **Status:** accepted (M10, 2026-11-13). Everything is tested against a deterministic fake gateway; **no real Razorpay account, key or webhook was used**. The test-mode run (T6) and the live launch (T7) are operator checklists in `docs/RELEASE.md` section E, and are **not done**.
- **Context:** until now an order became `paid` only through the browser callback (`/verify`) or the manual reconciliation script (M2). A customer who pays and closes the tab, or a callback that never arrives, leaves a paid order unrecognised; there was no way to return money; a payment arriving for an expired order was invisible. M10 makes the signed gateway webhook the source of truth, adds a scheduled backstop, and adds a refund ledger and service, without changing how checkout works.
- **Decisions**
  - **One code path, several doors (T1/T2/T5).** The webhook, the browser callback and reconciliation all end in `applyGatewayPayment` (conditional writes through the state machine: `awaiting_payment -> paid` only from `unpaid|failed`, amount/currency/gateway-order pinned in the `WHERE`). Whichever arrives first wins; the others are no-ops. The webhook does not call the gateway: the HMAC-signed body is the evidence, so it works when the gateway API is down.
  - **Authentication before anything.** `POST /api/payments/razorpay/webhook` reads the raw body as text, verifies the lowercase-hex HMAC-SHA256 with `RAZORPAY_WEBHOOK_SECRET` in constant time, and only then parses JSON. A different secret (the API key secret), re-serialised JSON, a missing or wrong-length signature, all 400 with no row written. No rate limit (the signature is the control; blocking the gateway's own retries would lose payments). 256 KB cap. `RAZORPAY_WEBHOOK_SECRET` is a separate secret (16+ chars): optional (warning) in `razorpay_test`, **required for `razorpay_live`** (`env:check` fails otherwise), ignored elsewhere.
  - **Dedupe (T1).** `WebhookEvent(provider, eventId)` is unique and stores no payload. A processed/ignored event redelivered is `200 duplicate`; a `failed` one is processed again; two concurrent deliveries both run, which is safe because every handler is a conditional write (tested with six in parallel: one `OrderEvent`). Status codes follow the gateway's retry behaviour: 200 for anything final (including ignored and unknown), 500 for a database failure so it retries, 503 when we are not configured (also retried: no event is lost to a mis-set variable).
  - **Out of order and duplicates.** `payment.failed` after success changes nothing (`failed_ignored`); `refund.created` after `refund.processed` cannot downgrade (pending moves forward only); `order.paid` after `payment.captured` is `already_paid`; a captured event for an order created under the other mode or with no recorded mode is never applied (`mode_mismatch`, `legacy_unclassified`).
  - **Orphan captures: money we cannot attach is recorded, not dropped (T5).** A captured payment whose amount or currency differs from the order, that arrives after the order was cancelled/expired, or that is a second payment for an already-paid order, is **not** applied. A `Payment` row (unique by gateway payment id) records it with the captured amount and a `reconcileReason`, so it is visible to staff and refundable. Reconciliation ignores these rows (`notIn ORPHAN_REASONS`) so a mismatched capture is never "fixed" by re-applying it. Auto-refunding was rejected: an unexpected payment may be a legitimate late payment the business wants to honour; a human decides, with one API call.
  - **Refund ledger (T4).** `Refund` rows in integer paise (CHECK amount > 0, currency INR). `pending` + `processed` hold balance, `failed` releases it. A refund request: (1) under a row lock on the payment (`SELECT ... FOR UPDATE`; without it two parallel requests both pass, shown by a mutation check) it validates the balance and **commits the ledger row**; (2) calls the gateway with the row id as `receipt`; (3) records the result. Writing the intent before the money moves means a crash or lost response can never lose a refund; `receipt` lets reconciliation find it. An unknown outcome keeps the balance held (never retried blindly: replaying the same `requestKey` returns the row); a definite rejection releases it; a refund the gateway never created is released only after 30 minutes and a successful empty lookup. Partial refunds keep the payment `paid`; processed refunds that sum to the whole payment move the payment, and the order's payment status, `paid -> refunded` through the state machine (actor `gateway`); the **order status is not changed** (cancel and refund are separate decisions; an invoiced order cannot be cancelled anyway).
  - **Gateway as truth for refunds.** Refunds made in the Razorpay dashboard arrive as `refund.*` webhooks (or the `--audit-refunds` pass) and are adopted as `source: gateway` rows, so the ledger equals the gateway ("refund ledger matches the gateway"). A refund we marked failed by guesswork is re-opened if the gateway later proves it exists. A webhook that disagrees with the ledger row it matches (amount) is flagged (`ledger_mismatch`), not applied.
  - **Who may refund.** New permission `refunds:write`, **owner accounts only**; the shared-password legacy session never has it (like `users:manage`). Every attempt writes `order.refund` to the audit log with ids and codes, never the reason text. The existing manual `paid -> refunded` bookkeeping stays for refunds made outside the system.
  - **Scheduled reconciliation (T3).** `reconcileGateway` = sweep (flag awaiting-payment attempts older than 10 min, at most once per 10 min each) + the existing flagged-attempt pass + refund reconciliation. It is exposed as `GET /api/internal/payments/reconcile` (same bearer-`CRON_SECRET` protection as order expiry) and `npm run payments:reconcile`. No cron entry is added to `vercel.json`: the schedule depends on the Vercel plan and is the operator's to set (a Vercel setting). The AC "a dropped-browser payment ends paid within one reconciliation cycle" is proven (fake gateway, clock advanced) with webhook and browser both lost.
  - **Launch gating (T7).** `razorpay_live` already needed live keys, production and `RAZORPAY_LIVE_ENABLED=true`; it now also needs the webhook secret. Rolling back is configuration only (`PAYMENT_MODE=request_only`); in-flight payments settle once live mode is briefly restored (documented, E4), because test and live data never mix (`mode_mismatch`).
- **Alternatives rejected**
  - Fetching the payment from the gateway inside the webhook before applying: doubles latency and fails when the API is down; the signature already authenticates the body. (Checkout verification still fetches, because the browser is not authenticated.)
  - Retrying unknown refund outcomes automatically: risks a double refund; reconciliation by receipt is safe.
  - Storing webhook payloads for audit: they hold customer data; the ledger, order events and outcome codes carry what is needed.
  - Marking an order paid for a mismatched amount "to be safe": a partial or different payment is not the order.
- **Consequences**
  - New environment variable `RAZORPAY_WEBHOOK_SECRET`; live without it fails the build by design.
  - New tables `Refund` and `WebhookEvent` (additive migration `20261119090000_m10_refunds_webhooks`; the app deployed before the migration fails only the new routes).
  - The fake gateway (`tests/support/fake-razorpay.ts`) now simulates refunds; it still throws on any other host.
- **Not done / needs you:** the real test-mode run (T6) and the launch (T7); auto-capture, refund policy and approvals, COD after launch, settlement reconciliation owner, reconciliation schedule (`RELEASE.md` E2); Razorpay behaviours the fake cannot prove (refund `receipt` echo, an idempotency header for refunds, refund-list pagination, the order `receipt` filter). Not built: refund UI, customer refund notifications, credit notes, partial-capture handling, disputes/chargebacks, settlement reports, retention/purge of `WebhookEvent` rows (a few hundred bytes each, one per gateway event; decide a retention period with the business, keep at least the gateway's retry window).
