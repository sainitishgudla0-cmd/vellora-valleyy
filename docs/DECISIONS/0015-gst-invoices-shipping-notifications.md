# ADR 0015 — GST, invoices, shipping rules, shipments and the notification outbox

- **Status:** accepted (M7, 2026-11-17)
- **Context:** orders carried prices and a delivery fee but no tax breakdown, no invoice, no pincode logic, no tracking and no notifications. The roadmap leaves open: the seller's GSTIN and registered address, the GST rate per HSN (accountant sign-off), e-invoicing (IRN) applicability, the courier partner, email/SMS/WhatsApp providers and a free-shipping threshold. None of these is the engineer's to decide, so each is configuration or data, and anything unconfigured fails closed.
- **Decisions**
  - **Prices are GST-inclusive** (the brochure MRP includes all taxes; wholesale and quoted prices follow the same convention). Tax is carved out of each line: `tax = round-half-up(amount x rate / (100% + rate))`, `taxable = amount - tax`, rounded once per **line** so every line, and so the invoice, is exact to the paisa (`taxable + cgst + sgst + igst = amount`, also a DB CHECK). Intra-state (place of supply = seller's state) splits `CGST = floor(tax/2)`, `SGST = tax - CGST` (SGST takes an odd paisa); inter-state is all IGST. Integer paise throughout, no floating point in any stored amount.
  - **Rates are data, not code.** `TaxRate(code, rateBp, effectiveFrom)` for an HSN (4, 6 or 8 digits; the most specific configured code wins) or the reserved `DELIVERY`, append-only per (code, date) so history is preserved. Set through `POST /api/admin/tax-rates` (owner only, audited). **No real rates are seeded or assumed**: the test fixtures use illustrative 5/12/18% values and say so. **CA review of the rates and of these rounding rules is still required before invoices are used for real** (acceptance criterion "CA-reviewed fixture set": the arithmetic fixtures are in `tests/unit/gst-core.test.ts`, ready for the accountant to check).
  - **Snapshot per order line** (`OrderItem.hsCode/gstRateBp/taxableValue/cgst/sgst/igst`, plus `Order.supplyType` and the delivery-charge tax) is taken at order creation from the rates in force that day. With no rate configured the order still works and the columns stay NULL; at invoice time the missing lines are computed from the rates in force on the **order's** date; if a rate is still missing the invoice is refused with the list of codes (`409 tax_not_configured`), never issued with a guessed rate.
  - **Seller** is configuration: `SELLER_GSTIN` (validated, and its state code must match the registered state in `site.address`) and optional `SELLER_LEGAL_NAME`. Missing or invalid = invoices refused (`409 seller_not_configured`); orders are unaffected.
  - **Invoices** (`POST /api/admin/orders/[id]/invoice`, explicit staff action for confirmed/paid/dispatched/delivered orders; automatic issue at dispatch is a later option): number `VV/26-27/000001` (financial year April-March by the Indian calendar, at most 16 characters, six-digit sequence), allocated from a row-locked per-year counter **in the same transaction as the invoice**, so numbers are gap-free (a failure after allocation rolls the counter back; parallel issuing yields 1..N exactly; one invoice per order by a unique index, repeat calls return it). The content is frozen into `Invoice.payload` at issue; the **PDF is a pure function of that payload** (own minimal writer, Helvetica, no dependency, no dates or random ids), so an invoice regenerates byte-for-byte whatever happens to rates, catalogue or settings afterwards. Business-account orders carry the buyer's company and GSTIN (B2B). Customers download their own invoice (`GET /api/account/orders/[number]/invoice`); staff via `GET /api/admin/invoices/[id]`.
  - **An invoiced order cannot be cancelled** (`409 invoice_issued` in the state machine): that needs a credit note, which is not built. Test-data cleanup also leaves invoiced orders alone so numbering cannot gain gaps. **Not built:** credit/debit notes, e-invoicing (IRN, QR) and e-way bills, GSTR export, amount in words, guest invoice download.
  - **Shipping rules** (`ShippingRule`: pincode prefix, serviceable, fee, free-above subtotal): with **no active rule the legacy behaviour is unchanged** (every pincode, site default fee); with any active rule the order's pincode needs a matching one (longest prefix wins, empty prefix = catch-all) and an unserviceable pincode is refused (`422`, nothing created or held) in every order path including quote acceptance, whose fee is still the quote's. `GET /api/shipping/quote` answers the same question publicly. The fee is added in `createOrder` inside the order transaction and taxed at the `DELIVERY` rate. The free-shipping threshold is a per-rule value, not a code constant.
  - **Shipments** (`Shipment`, `ShipmentEvent`): courier, AWB (unique per courier), https tracking link, a tracking graph (created -> picked_up -> in_transit -> out_for_delivery -> delivered, failed, returned). A shipment never moves the order's status (dispatch and delivery stay explicit, audited changes through the state machine; create the shipment first so the dispatch email carries the tracking). Customers see tracking history without staff notes. Courier APIs (live tracking, labels) wait for the courier decision.
  - **Notifications: transactional outbox.** `OutboxMessage(template, subject, dedupeKey unique, status, attempts, nextAttemptAt)` is written **inside the transaction of the change it announces** (order placed, confirmed, paid, dispatched, delivered, cancelled; quote priced; invoice issued), idempotent by dedupe key, so a message exists iff the change committed. It stores no personal data: content is rendered from the database at send time (templates are code, HTML-escaped). `processOutbox` (cron job `GET /api/internal/outbox/process`, bearer `CRON_SECRET`) claims messages with conditional updates (parallel workers never double-send), retries with backoff 1 min, 5 min, 30 min, 2 h, 6 h, gives up after 6 attempts (`dead`, retryable by staff), reclaims messages stuck `sending` after 10 minutes, and drops messages to erased customers. Provider errors are reduced to a short code (they can contain the recipient).
  - **Nothing can reach a real recipient from development or test.** The only provider is a mock with no network code (an in-process mailbox). `NOTIFY_MODE` is `off` by default (nothing queued or sent; avoids a stale-email blast when a provider is later switched on) or `mock` (development/test only: `env:check` fails the build if `mock` is set in preview/production). **There is no real provider yet, so no email is sent in production.** The email/SMS/WhatsApp provider is the business's choice; SMS also needs DLT registration. Customer sign-in codes (M5) still use their own mock and stay off in production for the same reason.
- **Consequences / open decisions**
  - Needs from the business: seller GSTIN and registered address, GST rates per HSN signed off by the CA, whether e-invoicing applies (turnover threshold), the courier partner, the email (and SMS) provider, the free-shipping policy and fee table.
  - Prepaid wholesale accounts, credit invoicing and payment collection follow in M10. The dispatch email carries tracking only if the shipment exists when the message is sent (normally seconds later).
  - A rate entered with a wrong past date changes what legacy lines compute at invoice time (issued invoices are frozen); there is no delete endpoint by design.
