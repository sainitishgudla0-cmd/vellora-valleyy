# ADR 0013 — Customer accounts, addresses, order history, consent and erasure

- **Status:** accepted (M5, 2026-11-15)
- **Context:** shoppers could only check out as guests; there was no order history, no saved addresses and no way to exercise DPDP Act 2023 rights (access/export, withdrawal of consent, erasure). The roadmap left the sign-in method open (phone OTP vs email OTP vs password), SMS needing DLT registration, and whether wholesale needs accounts.
- **Decisions**
  - **Sign-in: emailed one-time code, no password.** Nothing to leak or reuse, no password-reset flow, no SMS/DLT dependency. Guest checkout is unchanged and remains the default. Phone OTP can be added later next to it (the claim endpoint is where phone proof would plug in). Wholesale accounts are an M6 question; nothing here requires an account for any purchase.
  - **Delivery is a mock until M7.** `src/lib/auth/otp-sender.ts` has one sender, a mock that records codes in an in-process outbox (and the dev console outside tests). `CUSTOMER_OTP_MODE=mock` is refused by `resolveOtpConfig` (build gate `env:check`) in preview/production, and `currentOtpSender()` returns null there, so sign-in answers 503 instead of pretending to send. **Consequence: customer sign-in is effectively off in production until M7 adds a real sender.**
  - **Code design (`src/lib/auth/otp.ts`):** 6 digits from a CSPRNG, 10-minute life, one live code per address (issuing retires the previous), 5 guesses per code (atomic counter, concurrency-safe), 5 codes per address per hour, 30 s resend cooldown, plus per-IP limits at the route. That bounds guessing to about 25 attempts an hour against a 1-in-a-million code. The address and the code are stored only as keyed hashes (`HMAC(SESSION_SECRET, purpose:value)`). Responses never reveal whether an account exists (202 for any address; one generic 401 for any bad code). A first sign-in must accept the terms (`409 terms_required`, only after the code proved control of the address, and the code stays usable); that creates the account and its consent records.
  - **Sessions:** `CustomerSession`, same scheme as admin sessions (random cookie token `vv_customer`, only its keyed hash stored, revocable, `HttpOnly; SameSite=Lax`, Secure in production) with a 30-day absolute and 14-day idle life. A new sign-in replaces the browser's old session; logout (and `everywhere`) revoke server-side. Customer and admin cookies are separate and never valid for each other. Mutations get the same same-origin check as the admin API.
  - **Authorisation:** every `/api/account/*` handler except sign-in and logout calls `requireCustomer(req)` (ratchet test). The customer id comes only from the session, never from a body, query or path; request schemas are strict (unknown fields such as `customerId` are rejected). Ownership is part of the query itself (`where { id, customerId }`), so another customer's address or order is indistinguishable from a missing one (404).
  - **Addresses:** up to 10 per customer; the first becomes the default; one default at all times (partial unique index + customer-row lock, so parallel writes cannot break the limit or the rule).
  - **Order history:** summaries (cursor-paged) and detail. Detail never includes the guest access token, gateway ids, actor ids or staff-written reasons; status history shows only transitions.
  - **Linking (`Order.customerId`):** `POST /api/orders` links the order when a valid customer cookie is present (a bad cookie degrades silently to guest checkout; response shape unchanged). Past guest orders are claimed explicitly (`POST /api/account/claim`): by **verified email** (all unclaimed orders placed with that address, case-insensitive) or by **order number + access token** (possession of the guest link). An already-linked order is never re-linked; a wrong token, another customer's order and an unknown order all answer 404. Phone-based claiming is deferred (needs phone verification).
  - **Consent (DPDP):** append-only `ConsentRecord` (`terms_privacy`, `marketing`; granted/withdrawn; notice version `2026-11`). Marketing is opt-in and revocable (`POST /api/account/consent`). The notice text itself is the business's to provide; bump `PRIVACY_NOTICE_VERSION` when it changes.
  - **Export:** `GET /api/account/export` returns profile, addresses, consent history, orders (linked and guest orders under the same email), enquiries and newsletter status as a JSON download; no tokens, hashes or gateway ids; rate-limited and audited.
  - **Erasure:** `DELETE /api/account` with `{ "confirm": "DELETE" }` and a sign-in from the last 10 minutes (an older or stolen session gets `403 reauth_required`). Refused (`409 open_orders`) while any of the person's orders (linked or guest-by-email) is pending, awaiting payment, confirmed, paid or dispatched, because fulfilment needs the address. Otherwise one transaction deletes the account, sessions, addresses, consent records, sign-in challenges and newsletter row, **anonymises** the orders (name, email, phone, street, city, pincode, notes replaced; a fresh random access token kills old guest links; state, amounts, items and payment records kept for bookkeeping/place-of-supply), anonymises enquiries and removes stored idempotency replays (which hold order tokens). The audit row holds only the now-dangling opaque id. The person can register again with a clean slate.
  - **Audit:** claims, consent changes, exports and deletions write `AuditLog` rows with actor `customer:<id>`.
- **Not done / for the business to confirm**
  - **Legal retention:** which order fields must be kept, and for how long (tax/accounting), is for the business and its advisers; the anonymisation above keeps only amounts, items, state and payment records. Adjust `src/lib/account/erasure.ts` if more or less must be retained.
  - **No customer UI** (acceptance criterion: UI work waits for M8 approval): checkout does not prefill from saved addresses and there are no account pages yet.
  - Real OTP delivery (M7), phone proof for claims, and rate limits shared across instances (the per-IP limiter is in-memory; the per-address caps are in the database).
  - Someone can place a guest order with another person's email; that person, once verified, can claim it and would see the delivery address typed by the orderer. Low impact; noted.
  - Guest orders are not anonymised by erasure unless their email matches the account's.
